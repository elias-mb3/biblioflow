## Project Overview

**BiblioFlow** is a community library management REST API built for
Igreja Presbiteriana do Brasil (IPB) as a university extension project
(UNASP — Análise e Desenvolvimento de Sistemas). The system digitalises
and manages a community book collection: registering books, controlling
rentals (loans and returns), and accepting donations.

**Tech stack:**

| Layer | Technology |
|---|---|
| Language | TypeScript (strict mode) |
| Runtime | Node.js 20 LTS |
| HTTP Framework | Express 5 |
| Database | SQLite — single file, Docker-volume-persisted |
| ORM | Prisma 7 + `@prisma/adapter-better-sqlite3` |
| Validation | Zod 4 |
| Auth | JWT (`jsonwebtoken`) + bcrypt |
| Tests | Vitest 4 + Supertest |
| API Docs | swagger-ui-express + OpenAPI 3.0 |
| Code quality | ESLint + Prettier |
| Containerisation | Docker + Docker Compose |

## Architecture

### Layered design: `routes → controllers → services → repositories`

| Layer | Responsibility |
|---|---|
| `src/routes/` | Express router definitions; mount middleware, call controllers |
| `src/controllers/` | Parse HTTP request, call the service, return the response — no business logic |
| `src/services/` | All domain rules and business logic — single source of truth |
| `src/repositories/` | All database queries — no Prisma calls outside this layer |

Supporting directories:

- **`src/config/`** — `env.ts` (typed env vars) and `database.ts` (Prisma singleton).
- **`src/middlewares/`** — `authenticate`, `requireRole`, `validate`, `errorHandler`.
- **`src/schemas/`** — Zod schemas per resource; used by `validate` middleware.
- **`src/docs/`** — `openapi.ts`: full OpenAPI 3.0 spec served by `swagger-ui-express`.
- **`src/types/`** — Shared TypeScript interfaces (`AuthRequest`, `AuthPayload`).
- **`src/utils/`** — `AppError` class and `generateRegistrationCode` helper.

### Key architectural decisions

**1. English identifiers, Portuguese error messages**
Entity and field names use English (`fullName`, `periodDays`, `dueDate`) to
align with the broader dev community, while user-facing API error messages
remain in Portuguese to match the end-user context.

**2. `AppError` for controlled HTTP errors**
`src/utils/errors.ts` defines `AppError(message, statusCode, details?)`.
Services throw `AppError`; the global `errorHandler` middleware catches it
and serialises to `{ "erro": "...", "detalhes": [...] }`. This keeps HTTP
concerns out of the service layer.

**3. Prisma 7 adapter pattern**
Prisma 7 no longer reads `DATABASE_URL` from the environment automatically at
runtime. The client must be constructed with an explicit driver adapter:

```ts
// src/config/database.ts
const adapter = new PrismaBetterSqlite3({ url: process.env.DATABASE_URL });
const prisma = new PrismaClient({ adapter });
```

`prisma.config.ts` (generated by `prisma init`) is used by the Prisma CLI
only (migrations, generate). The runtime client uses the adapter.

**4. Prisma 7 generated client path**
`prisma generate` outputs to `src/generated/prisma/` with no `index.ts`.
All imports must target the specific file:

```ts
import { PrismaClient } from '../generated/prisma/client';
import { Role, RentalStatus } from '../generated/prisma/client';
```

**5. Prisma singleton via `globalThis`**
To avoid creating multiple database connections during hot-reload in
development, the Prisma client is cached on `globalThis`:

```ts
const globalForPrisma = globalThis as unknown as { prisma?: PrismaClient };
export const prisma = globalForPrisma.prisma ?? createPrisma();
if (process.env.NODE_ENV !== 'production') globalForPrisma.prisma = prisma;
```

**6. `registrationCode` is server-generated and immutable**
`src/utils/registrationCode.ts` generates a code in the format
`BIB-<timestamp_base36>-<6_random_hex>` (e.g. `BIB-LKZP3A4-C9F2E1`).
The `createBookSchema` intentionally does **not** include a
`registrationCode` field, so even if the client sends one, it is stripped
by `req.body = result.data` in the `validate` middleware.

**7. Zod 4 API change**
Zod v4 renamed `ZodError.errors` to `ZodError.issues`. All validation
error mappings use `.issues`:

```ts
result.error.issues.map(...)   // validate.ts
err.issues.map(...)            // errorHandler.ts
```

**8. Vitest `fileParallelism: false` for SQLite**
SQLite allows only one writer at a time. Running test files in parallel
causes `"attempt to write a readonly database"` errors when multiple workers
open the same `.db` file simultaneously. Setting `fileParallelism: false`
in `vitest.config.ts` serialises test file execution within a single process.

**9. Login identifier auto-detection**
`authService.login` detects whether the identifier is an email or CPF by
checking for `@`, avoiding a separate login endpoint per role:

```ts
input.identifier.includes('@')
  ? userRepository.findByEmail(...)
  : userRepository.findByCpf(...)
```

**10. OpenAPI spec as a typed TypeScript module**
`src/docs/openapi.ts` exports the full `OpenAPIV3.Document` spec as a typed
object. This avoids JSDoc comments scattered across route files, keeps routes
clean, and makes the spec easy to update in a single file. `swagger-ui-express`
serves it at `/api-docs` with the `explorer: true` option.

## Features

### Authentication — `src/routes/auth.ts`

| Method | Route | Auth | Description |
|---|---|---|---|
| POST | `/api/v1/auth/register` | public | Register MANAGER or USER |
| POST | `/api/v1/auth/login` | public | Authenticate, receive JWT |

**MANAGER** requires `email`; **USER** requires `cpf`. Enforced via
`z.superRefine` in `src/schemas/auth.ts`. Duplicate email/CPF returns `409`.
Passwords are hashed with bcrypt (10 rounds). JWT payload: `{ sub, role }`.

### Books — `src/routes/books.ts`

| Method | Route | Auth | Description |
|---|---|---|---|
| GET | `/api/v1/books` | 🔒 any | Paginated list (10/page) |
| GET | `/api/v1/books/search` | 🔒 any | Search by `title`, `author`, or `registrationCode` |
| GET | `/api/v1/books/:id` | 🔒 any | Get single book |
| POST | `/api/v1/books` | 👤 MANAGER | Create book (auto-generates `registrationCode`) |
| PUT | `/api/v1/books/:id` | 👤 MANAGER | Update book fields |
| DELETE | `/api/v1/books/:id` | 👤 MANAGER | Delete book (blocked if active rentals exist) |

Business rules enforced in `src/services/book.service.ts`:
- `registrationCode` generated on create; never accepted from client.
- Cannot delete a book with `status = ACTIVE` rentals → `409`.
- List returns `{ items, total, page, pages }`.

### Rentals — `src/routes/rentals.ts`

| Method | Route | Auth | Description |
|---|---|---|---|
| POST | `/api/v1/rentals` | 👤 MANAGER | Create rental |
| GET | `/api/v1/rentals` | 👤 MANAGER | List rentals (filter by `status`) |
| GET | `/api/v1/rentals/pending` | 👤 MANAGER | List overdue active rentals |
| GET | `/api/v1/rentals/:id` | 👤 MANAGER | Get rental detail with book and user |
| PATCH | `/api/v1/rentals/:id/finalize` | 👤 MANAGER | Finalize (return) a rental |

Business rules enforced in `src/services/rental.service.ts`:
- **Valid periods:** `15`, `30`, `45` days only — enforced via `z.refine` → `400`.
- **Stock check:** `activeRentals >= book.quantity` → `409`.
- **User rental limit:** `activeRentals >= MAX_RENTALS_PER_USER` → `409`.
  Limit is configured via env var `MAX_RENTALS_PER_USER` (default: `3`).
- **`dueDate` calculation:** `dueDate = startDate + periodDays`.
- **Late detection on finalize:** `returnDate > dueDate` sets `late = true`.
- **Double-finalize guard:** Finalizing an already `FINALIZED` rental → `409`.
- **Pending list:** queries `status = ACTIVE AND dueDate < NOW()`, ordered by `dueDate ASC`.

### Donations — `src/routes/donations.ts`

| Method | Route | Auth | Description |
|---|---|---|---|
| POST | `/api/v1/donations` | 🔒 any | Register a book donation |

Donation records the donor (`userId`), `title`, and `author`. The `bookId`
field is optional — the book may not yet exist in the catalogue. User
existence is validated before creating.

### API Documentation — `src/docs/openapi.ts`

Interactive Swagger UI served at **`/api-docs`** (no auth required to view).
The spec covers all 13 endpoints with:
- Request body schemas with examples
- Query parameter descriptions
- Response schemas for success and all error codes
- JWT Bearer security scheme — authenticate once via the **Authorize** button

## Data Model

Defined in `prisma/schema.prisma`. All tables use UUID primary keys.

```
User         — id, role (MANAGER|USER), fullName, phone, cpf?, email?,
               passwordHash, createdAt
Book         — id, registrationCode (unique), title, description, author,
               quantity, createdAt
Rental       — id, bookId→Book, userId→User, periodDays, startDate, dueDate,
               returnDate?, status (ACTIVE|FINALIZED), late, createdAt
Donation     — id, bookId?→Book, userId→User, title, author, createdAt
```

## Infrastructure

### Docker

`Dockerfile` uses a two-stage build:
1. **builder** — installs all deps, compiles TypeScript to `dist/`.
2. **runner** — installs prod deps only, copies `dist/` and `prisma/`.

Container startup runs `prisma migrate deploy` before `node dist/server.js`.

`docker-compose.yml` mounts a named volume `db-data:/app/data` so
`biblioflow.db` survives container recreation.

### Environment variables

| Variable | Default | Description |
|---|---|---|
| `PORT` | `3000` | HTTP port |
| `NODE_ENV` | `development` | Execution environment |
| `DATABASE_URL` | `file:./data/biblioflow.db` | SQLite file path |
| `JWT_SECRET` | *(must be set)* | Token signing secret |
| `JWT_EXPIRES_IN` | `1d` | Token lifetime |
| `MAX_RENTALS_PER_USER` | `3` | Simultaneous rental limit per user |
